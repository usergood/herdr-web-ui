# Project GitHub inbox and reviews

## Accepted scope

The owner requested project-scoped issue imports, incoming and outgoing PR review handling, review rules and validators, deduplicated requested-change work, re-review, guarded merges and updates of branches behind their target. This uses the already confirmed public HTTP API with temporary state and owned native-CLI fixtures, and the real browser journey seam. No new test seam is required.

Each Project detects `owner/repository` from its verified checkout on the owning Machine and explicitly selects a verified connection-server GitHub account, trusted reviewers, required GitHub check names, and independent automatic sync, fix import, branch update and merge policies. Repository standards provide default review guidance; existing custom review context is retained. All automation starts disabled. Remote Projects use a separately selected connection-server account for GitHub metadata; execution still follows their selected Machine.

Synchronization retains issues as Inbox Implementations without overwriting owner notes. PR snapshots contain reviews, requested reviewers, unresolved threads, check results, head/base revisions and GitHub branch protection. Review instructions are attached to imported work; foreign PR code is never executed to collect a snapshot. Requested changes create one Inbox Implementation per PR/head/review revision, preserving the standard factory specification, testing-seam and execution approvals. Pending reviews do not create fix work. Existing factory admission and worker limits continue to govern execution; import is not permission to run arbitrary PR code.

Automatic merging requires a non-draft PR, the current head and base, trusted current-head approval, no requested changes or unresolved threads, passing selected and required GitHub checks, and strict GitHub branch protection requiring reviews. GitHub remains the final authority when it receives the head-guarded merge. A behind branch may be updated with the expected head, after which checks and review are collected again. Conflicts and unsupported/missing protections remain blocked. No force push or bypass is used.

The owner can explicitly request re-review for a changed head; automatic polling re-requests only after an imported fix is marked implementation-complete and a new head is observed. Mutation intent is saved before a request. An ambiguous mutation is retained for inspection, never blindly retried. Every operation is serialized per Project, detects changed configuration/account scope, and records a durable result. Polling is bounded and pauses after failures.

## Manual production acceptance

Use a disposable GitHub repository first. Verify read-only sync, local note preservation, requested changes, a fix implementation, new-head re-review, behind-base update, failing checks, unresolved conversations and approval. Enable automatic merge only after branch protection is configured. The installation guide covers enabling the feature; it does not enable policies on existing Projects.

## Configuration

Open **Project settings → GitHub**. The repository comes from the verified checkout, including remote-only Projects, and stays read-only. Select a verified connection-server profile or import a saved native login. Pending profiles remain visible with their sign-in status. GitHub metadata supplies reviewer and branch-check choices under **Advanced GitHub automation**. Select the required reviewers/checks there and save, then independently enable issue imports, requested-change imports and automatic synchronization as needed. **Sync GitHub** performs the same bounded operation immediately. Remote-only Projects do not acquire a fictitious local execution checkout or account binding.

Open **Source** on a PR to read its file patches inside the application. The head is checked before and after loading. Binary or GitHub-omitted patches display their file status; a missing patch is never evidence that a file has no changes. **Import PR review** creates factory work with the frozen PR revision and Project review context. Imports do not bypass specification, testing-seam, Ticket graph or provider admission requirements.

Enable **Update behind branches** only for PRs owned by the selected account. Enable **Merge approved PRs** only with GitHub branch protection that enforces reviews, strict required checks and conversation resolution for administrators too. The policy also requires trusted approval on the current head and no pending reviewer requests. Missing protection, ruleset-only protection that this adapter cannot prove, failed/ambiguous mutations and inventories exceeding the bounded complete-snapshot budget stay blocked. Nested reviews, requests, threads, thread comments and checks are bounded at 100 each; top-level issues/PRs and file lists paginate. Incomplete snapshots cannot authorize mutations or fix imports.

Changing Project account bindings or checkout scope invalidates active operations and requires saving GitHub settings again. Polling is at least five minutes and backs off to at least fifteen minutes on failures. Mutation receipts remain visible across restarts and policy edits. After an ambiguous request inspect the retained receipt and GitHub state; the application does not blindly replay it.

## Issue readiness and automatic implementation

In **Project settings → GitHub**, enable **Automatic sync** and **Import GitHub issues** and save. Select and save a verified **Readiness account** separately from PR reviewers. Only that selected identity can authorize issue readiness. Triage labels inherit their canonical names unless mapped; a blocked label or conflicting roles prevents implementation. Old ready labels without current-scope evidence require renewed trusted readiness or explicit approval of the displayed issue revision.

**Preview eligible backlog** fetches current evidence and prepares sufficient trusted issue-body or approved app plans, including bounded Tickets and their authorization provenance. A plan must state scope, acceptance criteria, dependencies and testing seams. Missing decisions create real unanswered **Needs you** questions; preview never invents answers or enables execution. Every open repository issue stays visible, including excluded issues and their reasons. Owner notes and source history are retained.

Review the count and issue list, then choose **Enable automatic implementation**. This separate, default-off Project policy covers both the existing backlog and future eligible issues. Enabling requires the exact current preview and selected readiness identity; changes invalidate the preview. **Save queue settings** preserves the current opt-in. **Turn off automatic implementation** stops new automatic starts. **Pause queue** stops all new issue starts while admitted work continues. Move issues earlier or later to set priority and select an implementing Assignment limit within the global limit.

The existing synchronization loop prepares future trusted plans and dispatches the first eligible issue in board order through the same guarded admission as **Start prepared issue**. It reevaluates readiness, source/plan revisions, dependencies, queue policy and Project/global reservations before admission. A declared dependency requires verified intended PR coverage merged into the frozen target branch; an explicit release requirement also needs a containing published release. Issue closure alone is never delivery evidence. Cross-boundary, cyclic, missing, ambiguous or inaccessible dependencies remain blocked.

A sync outage retains the last visible state and problem, blocks new starts and leaves admitted contracts fixed. A known scope/readiness change or closure requests a controlled pause with **Needs you**, preserving produced work and uncertain reservations. Answering a question does not resume that frozen Run. Failed attempts require the owner's explicit **Retry** using current evidence; synchronization and restart never retry them. An uncertain native launch is reconciled by its original identity rather than replayed.

Configured checks and independent Standards and Spec reviews still apply. Current checked/reviewed work can release implementation capacity while its Assignment remains **Awaiting merge**, allowing unrelated eligible work to start. Owner acceptance, issue/PR publication, merge, release and deployment retain their separate approvals. Enabling implementation does not enable any of those actions or migrate historical delivery records. The fictional demo reports automatic execution as unavailable and never starts a native agent.
