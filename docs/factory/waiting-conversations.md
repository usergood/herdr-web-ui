# Waiting conversations

Factory coordinators waiting for child work and conversations asking recorded owner questions can yield execution capacity while retaining their Run, native pane, worktree, history and ownership. This is internal waiting; it does not mark the Assignment owner-Paused or finish a Ticket. Implementation, integration, checks and independent review still use their existing controls.

A recorded question or queued child request creates durable parking intent. The app releases capacity only after observing the same owned native identity at rest, without background work. A native permission prompt, unknown execution or disconnected Machine keeps its reservation. Interrupted build reservations remain separate and occupied. A lost observation is retried automatically; a parking request alone is never proof of rest.

After all current questions have answers or the requested children reach rest/completion, the continuation joins the same global queue as Start and child requests. Its waiting age begins when it becomes eligible and survives restart and recoverable observation attempts. Admission reserves capacity before sending a bounded continuation prompt to the same native conversation. Child answers resume the child that asked them, using normal capacity. Native question synchronization and answer-consumption receipts retain their worker identity; they cannot borrow another conversation's reply. A conversation that already consumed the exact answered revision needs no duplicate notification.

Inbox's Factory capacity panel shows executing reservations separately from waiting conversations, including waiting for native rest, released capacity, waiting to resume and delivery uncertainty. Saving an answer remains available at capacity. An explicit Send answered context joins or observes the same continuation instead of bypassing admission or duplicating delivery. New records use the same authenticated factory endpoints; public `FactoryRun.continuation`, `FactoryWorker.continuation`, `capacity.continuations` and continuation entries in `capacity.waiting` expose progress without tracker credentials. `send-answers` can return `queued`.

Before delivery the app durably records `sending`. A lost response or a restart during delivery becomes uncertain and is never replayed automatically. Its reservation and explanation remain visible: inspect the native conversation through its existing controls before deciding what to send, or Stop that owned attempt. Native busy refusals return to observation. A native input draft blocks resumption and remains an owner concern. The app never approves a native permission prompt or fabricates an answer-consumption receipt.

The scoped tracker adapter supplies child identity automatically for questions, native synchronization and answer consumption. Execution Machines accept authenticated `operations/send-worker` only for an owned resting worker, preserving native permission and input-draft checks. Copied recovery state never activates continuations.

Validation uses authenticated public HTTP/API with disposable Machine/Herdr/repository fixtures and the real desktop/mobile browser client. It covers normal capacity one across Ticket implementation, backend integration, independent review and coordinator resumption; owner answers at capacity; exact child identity and consumption; restart, lost observations, native permission waits, interrupted builds and lost delivery responses. `scripts/factory-parking-browser-regression.ts` covers saving an answer, queued progress, reload and automatic resumption on desktop and touch layouts. These fixtures launch no paid agents and are not native provider certification.
