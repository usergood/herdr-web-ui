# Interface cleanup and issue-driven factory

Product choices confirmed during the owner's Q1–Q29 interview on 2026-10-13. This is a design record for subsequent Specification and Ticket planning; it does not claim the capabilities are implemented or activate any live policy. It revises the earlier manual-start, board-lane and implementation-completion direction while preserving existing unrelated contracts.

## Agreed behavior

- Completion defaults to verified merge into the Project's delivery branch. A Project can instead require a release containing the merge. Freeze that setting when an Assignment starts. Repository changes, including documentation and already-committed changes, require this delivery milestone; a clean working directory is insufficient evidence. Research retained as app artifacts without repository changes can be accepted manually. An unreachable Machine means the change set is unknown.
- Discard explicitly stops and reconciles active work, then moves the Assignment to Done with a Discarded outcome and hides its sidebar entries. Retain history, artifacts and branches; do not automatically delete files or close remote PRs. Unconfirmed stopping leaves Needs you / Discard pending. Archiving finished Assignments remains a separate later action.
- The Project sidebar keeps unfinished Assignments and active chats. Remove its Inbox/Assignments shortcuts and headings. A Project name opens its board. Settings and Add message belong at the board's top right; global Inbox remains reachable from the app header.
- Keep Assignment, Ticket and Run as the canonical terms. See the [root glossary](../../GLOSSARY.md).
- The board has exactly Inbox, Queued, Running, Needs you and Done lanes. Activity is conveyed by an icon and a short label, including Specifying, Implementing, Validating and Reviewing. Ticket progress is shown only when Tickets exist. Detailed history remains accessible from the card.
- Inbox holds untriaged or unselected work. Queued means selected for its next action but not started. Running means work is underway. Needs you means an answer, approval, repair or manual merge is required, taking precedence even if another worker continues. Done means delivered, accepted without repository changes, or discarded. Recovering connections stay Running; unresolved interruption/failure needs attention. Passive external waits use Running / Awaiting checks or release, without busy animation, unless owner action is required.
- Mobile Inbox follows the existing Settings design.
- Use the pinned skills' five default triage roles and labels: needs-triage, needs-info, ready-for-agent, ready-for-human and wontfix. Projects can override the mapping and inherit the defaults when no override is set.
- ready-for-agent means planning has already happened and the issue should automatically start implementation without repeating planning. Each Project explicitly enables this behavior, accepting readiness only from its owner or configured trusted maintainers/automation. Other issues remain in Inbox until the owner starts planning. ready-for-human and wontfix do not dispatch agents; conflicting triage labels require correction.
- Batch GitHub issue publication is included: review a planning session's proposed issues, acceptance criteria and dependencies together, then explicitly publish them and mark eligible issues ready-for-agent. Completing a planning chat alone does not publish. One independently deliverable issue maps to one Assignment/PR, linked to the originating plan and dependencies. Internal bounded work remains Tickets. Inseparable work remains one Assignment.
- Ready issues skip repeated planning but retain their approved issue revision, acceptance criteria, confirmed testing seams, Project checks and independent Standards and Spec reviews. Missing requirements or new design choices go to Needs you; merge approval remains manual. The existing unstructured direct Work path is not sufficient by itself.
- Scope changes or readiness removal before dispatch revoke eligibility pending renewed readiness. Changes after dispatch raise Needs you and request a controlled pause, preserving produced work and reconciling unreachable workers. They do not alter the active contract or launch duplicate work.
- Initially allow one implementing Assignment per Project, configurable within existing global agent/build limits. Respect explicit dependencies and board priority. Pause queue stops new starts while current work continues. Reconcile existing Runs after restart before dispatching more. Failed attempts require owner Retry.
- A dependent Assignment can start once the required changes are verified merged into its target branch. It waits for release only if it explicitly requires a released artifact. Automatic stacked PRs are outside this scope.
- Successfully finished implementation, checks and independent reviews release the implementing slot while the Assignment remains Needs you / Awaiting merge. Independent work can proceed. Active or uncertain workers/builds retain their reservations until reconciled.
- Automatic implementation-PR publication is a separate Project opt-in, off by default. Otherwise the owner explicitly selects Publish PR. When enabled, publish only the approved Assignment branch/diff after passing checks and independent reviews. Merge approval remains manual.
- Batch publication retains created issues and resumes without duplicates. Hold every Assignment in the batch from automatic dispatch until all issue identities and dependency links are confirmed. Reconcile ambiguous results before retrying and preserve successfully published issues rather than deleting them as rollback.
- Delivery requires verified PR merges covering all intended changes in the configured repository and target branch, followed by a containing release when required. Missing or ambiguous linkage goes to Needs you for correction or Discard. Closing an issue or an unmerged PR does not prove delivery. Non-PR delivery is outside this scope.
- Preserve historical records and archived state during migration. Reconcile unarchived Done items: verified delivery and accepted no-change research stay Done; unmerged changes or missing evidence become Needs you with an explanation. Never restart old work automatically.
- Initial scheduled operations are built-in GitHub sync and upstream sync, with per-Project schedules, enable/disable, Run now and result history. Reuse GitHub import behavior.
- New schedule defaults: GitHub sync every 15 minutes and upstream release checks daily at 03:00 in the saved Project time zone, initially America/Mexico_City here. Preserve existing polling settings. Perform at most one catch-up per overdue job after downtime; do not overlap a Project job. Expose failures with retry/backoff and Run now. Values are editable; live enabling remains a Project setting action.
- Upstream sync checks daily for releases, not every upstream main commit, and creates no duplicate work when there is no new release.
- Upstream integration is prepared and validated in isolation, then waits for manual approval. The owner wants possible future low-risk automatic merging, but accepts manual approval for this scope. No automatic merge, publication or deployment policy is activated by this discussion.
- The release detector creates one Assignment for a new upstream release and follows the normal planning/approval steps before implementation. Already planned ready-for-agent work should enter the implementation flow described above. No separate standing approval for arbitrary unattended upstream preparation is inferred.
- Keep a pending upstream update's approved release fixed. Record only the newest subsequent release as the next candidate, then offer one follow-up after the current Assignment is merged or discarded. A discarded release is not requeued without a fresh owner action. Preserve active scope and avoid daily duplicate Assignments.

## Validation direction

Reuse the confirmed public HTTP/API with disposable state and owned fixtures, and real browser journeys. Apply TDD at those confirmed seams when implementation is authorized. Cover mobile navigation, lane/activity rendering, delivery and discard guards, historical reconciliation, trusted readiness and changed scope, batch recovery without duplicate starts, dependency admission, queue pause/restart/limits, scheduler catch-up and overlap, upstream candidate coalescing, and PR/release evidence. Contract changes must include both client/server handling and the demo transport. Independent Standards and Spec review must examine the resulting implementation at the same checked revision.
