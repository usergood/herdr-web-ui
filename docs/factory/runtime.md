# Saurons eye runtime

The owner requested implementation of the full specification and confirmed both testing seams: the public HTTP interface with temporary state and owned fixtures, and the real browser client. SQLite and the app-native Other tracker are the initial implementation choices. Existing native chats and terminals remain available before factory preparation.

## Start and configure

Open Inbox, capture an Implementation, and add chats, notes or attachments. Select a Project later without changing the Implementation's identity. Register an existing Git checkout and verify another checkout for each execution Machine. Machine onboarding uses the existing SSH dialog with `user@hostname` or an address; an SSH alias is optional.

Configure known check and setup recipes as JSON argument arrays, execution permissions, task environment and shared document paths. Recipes run without shell interpolation. Native contexts and checks get private cache, temporary, database and notes directories; programs should honor the supplied `PORT=0` and `FACTORY_*` environment. Dependencies are installed by the explicitly configured setup recipes. Ignored secrets are not copied from the primary checkout.

For remote execution, the selected Machine must reach the connection server's authenticated app address. `HERDR_FACTORY_PUBLIC_URL` selects that HTTP(S) callback origin; otherwise the request origin is used. `createServer({ factory: { publicUrl } })` provides the same per-instance configuration. Use the deployed HTTPS or reachable private-network address when a browser connects through localhost. SSH onboarding does not require an alias.

Prepare this Machine verifies the complete pinned source under private application state. It installs no global plugin. A Run freezes the source commit and every locked file hash, the effective provider/Machine, verified checkout/base/instructions, specification, graph, approvals, artifact references and permissions.

The connection server owns `stateDir/factory/records.sqlite`, immutable blob files and history. Machines own their operational leases, native sessions and worktrees. SSH never shares a SQLite file. Keep a separate state directory, port and Herdr session for development; use the repository's `check` runner for acceptance.

## Work, review and history

Assignment details and the Project sidebar now preserve named Specifications, Orchestrator and Human Review entries across native-context handoffs. Ticket implementations, independent reviewer contexts and repair histories retain their original parentage and provenance. Orchestrator starts automatically after new Specification acceptance as described above; Checked and independently reviewed PRs now hand off automatically to Human Review as described below. See [Workflow conversation history](workflow-conversations.md) for the current behavior and wire metadata.

The integration branch and worktree belong to the Run. Implementers receive separate worktrees at the current integration tip. The scoped tracker exposes stable Ticket IDs, accepted context, questions, versioned answer consumption, worker operations, checks and proposal operations. Its private capability lives in a 0600 file and cannot approve specifications or control another Run.

Only the dependency frontier can start ordinary Ticket work. Shared document claims exclude competing writers. Workers reconcile the current integration tip, run the configured checks and submit a committed candidate. The serialized backend merger rejects stale tips, changed cwd/branch/repository, dirty tracked changes, unclaimed shared documents and committed application scaffolding. It retains the branch and never updates the default branch.

The native adapter includes an exact request guide and `bun .saurons-eye-tracker.mjs help`. For historical Runs, a blocked worker remains an owner-answer gate and a ready worker awaits explicit checks/integration. New Specification-authorized plans are driven automatically as described below. Integrating all accepted Tickets moves the stored lifecycle stage to review; the board presents its lane and current activities separately; acceptance still requires current evidence and does not infer publication.

Agent-context reservations cover active and uncertain app-managed execution globally across Projects, providers and Machines. The default normal limit is six Agent contexts, with one additional shared interview/pre-approval Specification context; implementation and review cannot use that allowance. Builds have a separate default limit of two. Inbox exposes Factory settings and recovery. Ready chats consume no execution slot but retain their worktree ownership. Ordinary terminals and independently launched agents are excluded.

Start and child-worker requests durably queue when capacity is occupied. The dispatcher reconciles accepted identities and admits the oldest eligible request without preempting running work. Request identity, purpose, waiting age and reservations survive restart; dependency-blocked work does not block eligible requests. Capacity and reconnect waits recover automatically. Machine recovery uses six bounded attempts with backoff, then shows the remaining problem and required inspection in the capacity panel. Unknown launches keep their reservations and are observed rather than launched again. Queue metadata is public; retained request bodies and tracker credentials stay private. Cross-machine failover is not implemented.

Waiting coordinators and owner-question conversations now retain a durable continuation independently of their execution reservation. Native rest must be verified before capacity is released; answers or resting child results resume the same native identity through the global queue. Unknown execution, native permission prompts and interrupted builds retain their reservations. The capacity panel separates waiting conversations from executing contexts. See [Waiting conversations](waiting-conversations.md) for recovery and wire behavior.

Branch review compares the recorded base/head. Workspace review captures staged, unstaged and untracked changes. Snapshots are immutable and private generated files are excluded. Findings retain snapshot/path/side/line/hunk anchors; changed captures mark them outdated. Request changes freezes only the selected drafts. A delivered batch can start an owned rework worker. Resolution and acceptance require fresh checks and separate native Standards and Spec reports at the current head.

Artifacts have hashes, size limits, versions, provenance, annotations and source/download actions. HTML uses an opaque sandbox and restrictive CSP. Imported remote outputs remain available centrally while the Machine sleeps. Referenced deleted versions retain their blobs for historical and retrospective evidence. The blob quota includes retained blobs; backups and native checkouts occupy additional storage.

Stop releases only the verified owned native resources and retains work/history. Cleanup checks every generated file, refuses unexpected or ignored outputs and uncommitted changes, and removes only clean stopped checkouts. It preserves Git branches and sibling notes. Native conversation pages can be retained explicitly and a Stop attempts a final capture; unavailable or older native pages remain a visible import limitation rather than an invented transcript.

Assignment execution controls provide Pause and Resume without requiring agent capacity or Done/archive eligibility. Pause durably blocks dispatch before stopping every owned attempt, child and build. Offline or uncertain resources leave Pause pending with Machine/Run reasons and retain their reservations; shutdown is reconciled automatically after reconnect and restart. Paused is a status within the existing board lane. Worktrees, dirty and ignored edits, retained conversations, approvals, completed Tickets and check evidence remain available.

Resume queues only retained unfinished contexts at global capacity. The native continuation uses the same Run/worker and worktree and receives a bounded handoff from its captured history; earlier captured pages remain available. Changed accepted Specification/graph authority blocks continuation for reconciliation rather than silently reusing stale evidence. Completed work is not restarted, and unchanged scope requires no renewed approval. Pending Delete authority takes precedence over Resume. Lost continuation responses are observed without replay; a Machine's durable proof that continuation never started permits safe automatic requeueing.

Retrospectives use only a selected retained Project evidence set. Candidates are immutable records. Approval and Apply in a new worktree are separate actions; the pinned retro action presents candidates without applying them.

Delete Assignment is available on every Assignment, including failed, stopped, paused and unfinished work. Its confirmation lists the destructive scope and exclusions. Delete durably blocks dispatch and further writes without consuming an agent slot, reconciles every attempt's owned native contexts and builds, and removes verified owned dirty/ignored worktrees, Assignment-only local branches, notes, caches and temporary data. The primary checkout, sibling work, shared Project resources, independently referenced attachments, pushed branches and PRs survive. Exported copies and external provider history are excluded.

Offline or uncertain execution and changed resource identities remain Delete pending with Machine/Run reasons; reconnect and restart automatically reconcile the retained cleanup journal. Uncertain reservations remain held until the Machine confirms shutdown and cleanup. Repeated Delete and late allocation/check responses cannot restart work or restore purged records. After every required obligation is confirmed, final deletion purges owned history/records and removes the Assignment from navigation without certifying delivery. Delete now purges existing app-managed snapshots and recovery copies, including nested copies and their snapshots, before confirming the recovery obligation. Backup cleanup cannot finalize Delete while a Machine or GitHub obligation remains unconfirmed.

Linked GitHub issues are permanently deleted through the selected repository's verified GitHub identity; closing an issue is not sufficient. Before asynchronous cleanup, Delete retains a repository/source fence that blocks automatic issue import, PR repair intake and retained-PR mutations, including stale synchronization already in flight. Suppression applies across Projects for that repository. PRs and pushed branches remain; a fresh explicit owner PR import creates distinct work.

The Delete panel shows pending GitHub permission, account, transport and receipt problems after local cleanup. Repository-admin permission and organization deletion policy still apply. Reconciliation verifies a bounded, paginated issue inventory before sending a deletion; an already-missing issue completes safely. Lost or ambiguous replies remain pending until confirmed by a later observation, and confirmed cleanup is not repeated while another obligation remains. Restart resumes the same authorized identity and journal. After final cleanup, source fences contain only repository/source identifiers, without Assignment content/history. Sanitized app-managed snapshots and recovery copies retain these content-free fences, so restoring older data cannot re-enable automatic import or retained-PR mutations for deleted work.

## Board progress

Assignments use five board lanes: Inbox, Queued, Running, Needs you and Done. Cards with Tickets show named active work and an expandable complete Ticket list with waiting/running/completed counts and dependency, capacity or failure reasons. The disclosure supports keyboard activation and stays open when changing progress moves a card between lanes.

Activity tags reflect retained Run, worker and check evidence: Specifying, Implementing, Testing, Auto-Review and Fixing can overlap. Configured shared document paths are claimed conservatively for each worker, so competing shared writers wait. The coordinator releases capacity only after verified rest and remains parked while the backend processes candidates, including at a cap of one.

Native rest is a candidate signal. The backend reconciles identity, refreshes against the integration tip, runs Project setup/check recipes under the separate build reservation and integrates through the serialized merger. Only retained integration receipts complete Tickets. Completed Tickets and check identities survive restart; uncertain launches, check replies and merger replies are reconciled rather than replayed. ## Backup, restore and rollback

Create verified backup captures the database and referenced blobs under one SQLite reservation, verifies hashes and publishes a private directory. Restore verifies schema, integrity and every blob, then creates a separate state directory with execution disabled. It never replaces the working state or activates native leases.

Delete rewrites app-managed snapshots to remove owned records, references and exclusive blobs while preserving independently retained shared Project evidence, its valid hashes/approvals, and other Assignments. Future backups also retain the blobs owned independently by Project evidence. Snapshot database/manifest publication uses a recoverable hash journal; interrupted rewrites remain Delete pending with a concrete reason and retry after restart. Abandoned unpublished backup/restore staging directories are removed under the same reservation. Backup and restore reconcile pending deletion fences before publishing, so concurrent or later copies cannot reintroduce deleted content. Exported copies and external provider history remain excluded.

For an upgrade rehearsal, restore a copy, start an isolated instance against that copy, and inspect retained records and artifacts through the UI/API. Keep the original service, checkout and state unchanged. Run the previous compatible application against its own restored copy to rehearse rollback. A newer unsupported schema fails closed. Promotion, credential/device migration and service changes require a separately chosen deployment target and owner dispatch.

Backups cover application records and imported blobs. Git repositories, native transcript stores, worktree outputs that have not been imported, SSH credentials and device/transport configuration require their own machine backups. Do not claim those are present in a database/blob restore.

## Human Review handoff and discussion

After automatic checks and independent Standards/Spec review pass and the PR is published, Orchestrator parks at verified native rest. The app captures the branch diff and retains one Human Review handoff per Run. Open Human Review in Workflow history to navigate its directory/file list beside the discussion and retained native history. Snapshot ID/hash, Machine, base/head, change status and rename paths identify the captured result. Binary files have no text diff; files or diffs over 2 MiB show a size notice. Captures are bounded to 200 files and 16 MiB. Reading captured files/history works without a free Agent context or a connected execution Machine.

The execution bridge must advertise `human_review_protocol: 1`; older bridges keep a visible upgrade reason and never launch the assistant through their direct editing-work path. Send discussion explicitly queues a retained owner message through normal global capacity. The first admitted message starts a separate read-only Human Review assistant at the captured commit; later messages resume that same conversation. A confirmed stopped context is replaced only for a new explicit message, retaining the logical entry, prior native history and a bounded handoff of the discussion. It cannot use the planning allowance or dispatch competing implementation/review work. Verified native rest releases its capacity, and replies are retained automatically. Unknown deliveries retain their identity and uncertainty rather than replaying a message after restart. Machine and capacity waits remain visible. Discussion grants no repair or merge authority; explicit approval is required for any merge.

Select a Before or After line number in the captured diff with keyboard, mouse or touch. For a range, choose its first line, then Select range end and the final line on the same side; Shift-click also extends a selection. Save draft finding persists the comment on the connection server. Saved drafts survive file navigation, reload and server restart, and remain separate from submitted history. Edit draft changes only the text; Remove draft removes an unsent comment. These controls need no Agent context and launch no repairs or approvals. Binary/oversized captures have no selectable lines; ranges must consist of captured lines on one side and span at most 101 lines.

Each comment retains its exact snapshot, captured head/hash, path, change identity, side, inclusive range and original hunk, including renamed and deleted files. A later changed capture marks earlier anchors stale, including late saves against the old snapshot. Stale drafts remain visible and editable without moving their anchors; Original anchor exposes the retained revision and hunk for reconciliation. Submitted/resolved history cannot be edited or removed through draft controls. Drafting does not grant merge authority.

## Human Review approval and delivery

Approve and merge is one explicit owner control for the displayed snapshot/head, with no Agent context reservation. It retains a revision-bound approval and revalidates the latest configured checks, independent Standards/Spec reports, published PR and frozen repository/target. Existing unresolved comments block approval without comments; unfinished line-comment compositions and discussion drafts disable the button, including while browsing other files. The historical Accept reviewed head control cannot complete automatically planned work.

The execution Machine uses its frozen verified GitHub account and owned checkout. It checks current PR identity, GitHub mergeability, review/conversation requirements and any frozen Project GitHub validators/trusted reviewers. It never overrides protection or retries a sent merge mutation. Permission refusals, conflicts, stale evidence and unknown outcomes remain visible. Duplicate approvals and bridge restart reconcile the retained PR identity instead of submitting another merge. Unknown outcomes use bounded backoff and expose a blocked reason after six observations; repeating the same approval observes its existing intent. Awaiting releases are observed every thirty seconds.

Delivery milestone in Project execution settings is frozen with the Run: verified merge (the default) or containing release. Done requires GitHub's exact-head merge receipt and confirmation that the authorized target contains its merge commit. A release milestone remains in review after merge until a published, non-draft, non-prerelease tag contains that merge. Approval observes releases; it creates no tag or release and grants no deployment authority. The detail API retains approval provenance, merge commit, release tag and unresolved reasons in `human_review_approvals`.

Coverage uses disposable native Git/GitHub fixtures and authenticated HTTP (`server/factory-human-merge.contract.test.ts`), plus desktop/mobile approval, failure and delivery journeys (`scripts/factory-human-merge-browser-regression.ts`, registered in the browser lane). Fixtures do not merge owner work, launch paid agents or publish releases.
