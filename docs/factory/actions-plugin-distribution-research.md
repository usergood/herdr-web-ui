# GitHub Actions and Herdr plugin distribution audit

Research date: 2026-10-11. Fork source baseline: `c7cdd569b431757a58f771a0369bce1b46c5f291`. Herdr source: stable **v0.9.3**, commit `7b116c05bfda646af39d2524c54e70c751f57ee8`. This is a source and read-only metadata audit, not a captured network trace. No workflow was enabled or dispatched; no repository topic, release, tag, plugin installation, or service was changed.

## Plugin distribution and publication

**Saurons eye is already packaged as a Herdr plugin. It is installed directly from our GitHub repository; nothing needs to be uploaded or merged into `herdrdev/herdr`.** The manifest identifies `usergood.saurons-eye`, displays **Saurons eye**, declares version **0.4.7** and requires Herdr **0.9.0+**. It supports Linux, macOS, and Windows. Its install-time commands check prerequisites, run `bun install`, and build the browser application. Its startup hook launches the application; its actions start/stop/report status and open phone setup. [Fork manifest](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/herdr-plugin.toml#L1)

### Direct installation

For the audited fork revision, the explicit command would be:

```sh
herdr plugin install usergood/herdr-web-ui --ref c7cdd569b431757a58f771a0369bce1b46c5f291
```

This command is documentation only and was not run. Both bundled installers target `usergood/herdr-web-ui` and the fork plugin ID. They require an owner-selected reviewed ref before proceeding. The shell installer passes `--yes` to Herdr; the Windows installer does the same. [Shell installer](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/install.sh#L17), [ref guard and install](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/install.sh#L139), [Windows installer](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/install.ps1#L64)

Herdr v0.9.3 initializes a temporary Git checkout with `origin=https://github.com/owner/repo.git`, fetches the requested ref at depth one, and checks out the resolved commit detached. **Without `--ref`, it fetches the repository's default-branch HEAD, rather than selecting the latest release.** It previews the manifest, runs supported build commands after confirmation, verifies the manifest did not change during the build, then registers the plugin locally as enabled. The stored source metadata includes the requested ref and resolved commit. These are local installation operations, not a marketplace publication. [Exact checkout behavior](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/cli/plugin.rs#L865), [installation and registration](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/cli/plugin.rs#L196)

Herdr's installed-plugin registry is user-wide and shared across that user's sessions. Reinstalling a GitHub-managed plugin replaces its managed checkout; plugin config/state remain separate. A locally linked plugin cannot be silently replaced by a GitHub installation. There is no dedicated v0.9.3 `herdr plugin update` command. Plugin commands run with the user's permissions and inherited environment; Herdr validates manifests but does not sandbox or review the executable code. [Official CLI documentation](https://herdr.dev/docs/cli-reference/#plugins), [pinned trust documentation](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/docs/versions/0.9.1/website/src/content/docs/plugins.mdx#L35)

If prerequisites are missing, our shell installer executes the official Herdr and Bun installers and downloads checksum-pinned Node from `nodejs.org`. The Windows installer downloads the official Herdr installer and executes Bun's official PowerShell installer. Package installation/build may then fetch package-registry dependencies. These network effects happen on the installation machine, separately from GitHub Actions. [Shell prerequisite installation](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/install.sh#L103), [Node download](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/install.sh#L37), [Windows prerequisites](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/install.ps1#L27)

### Public marketplace listing

Herdr's public marketplace is a discovery index of GitHub repositories. Eligible repositories opt in by adding the `herdr-plugin` GitHub topic and a parseable manifest on their default branch. The index refreshes approximately every 30 minutes. There is no plugin-package upload or maintainer review queue; listings are unreviewed. **Current rules exclude GitHub forks.** [Official marketplace rules](https://herdr.dev/docs/marketplace/)

The read-only GitHub API returned `fork: true`, `private: false`, parent `devswha/herdr-web-ui`, default branch `main`, and `topics: []` for this repository. Therefore this repository is directly installable, but it is ineligible for that index under the documented fork rule, even if we add the topic. A separately published non-fork repository could qualify; that would be an owner decision, and was not created. [Repository metadata API](https://api.github.com/repos/usergood/herdr-web-ui)

Adding a topic would change public repository metadata, not install the plugin or write to the Herdr source repository. Enabling Actions alone does not add the topic. No audited workflow submits a listing, opens a PR in Herdr, or pushes to the original web-UI repository. This last conclusion follows from the workflow targets, rather than a marketplace-specific API guarantee. [App release target](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/.github/workflows/release.yml#L55), [bundle publication target](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/.github/workflows/remote-bundles.yml#L115)

### Releases and installed-app updates

The manual **Release** workflow publishes a `vX.Y.Z` Git tag and GitHub release to **the repository running the workflow**, through `GH_REPO=${{ github.repository }}`. In this fork that is `usergood/herdr-web-ui`; it is not `herdrdev/herdr` or `devswha/herdr-web-ui`. Publication requires an explicit workflow dispatch on `main`, version/notes validation, and the reusable CI workflow before the job obtains `contents: write`. It creates the tag at the exact validated SHA. Its current display title still says “herdr web ui”; that is branding left to correct before our first fork release. [Release workflow](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/.github/workflows/release.yml#L1)

GitHub metadata currently shows **no fork GitHub releases**, but it does show inherited source tags through **v0.4.3**. The v0.4.3 tag still contains plugin ID **`devswha.herdr-web-ui`**, not our fork ID. A generic “install the latest existing tag” process can therefore select the original application identity and omit fork features. The current fork source/package version 0.4.7 does not mean that a fork `v0.4.7` tag was published. Prefer the reviewed fork SHA until a deliberately versioned fork release exists. [Fork tags API](https://api.github.com/repos/usergood/herdr-web-ui/tags), [fork releases API](https://api.github.com/repos/usergood/herdr-web-ui/releases), [inherited v0.4.3 manifest](https://github.com/usergood/herdr-web-ui/blob/v0.4.3/herdr-plugin.toml#L1)

The managed application updater uses the installed checkout's `origin`, fetches ordinary `vX.Y.Z` tags, ignores `remote-v*` and prerelease tag forms, verifies ancestry, then builds and health-checks a separate release checkout. It preserves the user's selected origin in that new checkout; it does not hardcode the original project's repository. **A tag is sufficient for update discovery, even when there is no GitHub release page.** This is why release tags must not be pushed casually. [Tag discovery and ancestry](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/server/updater.ts#L202), [release staging/origin preservation](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/server/updater.ts#L264), [release procedure](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/docs/development.md#L338)

The current fork defaults to **manual checks and installs**. Periodic discovery only starts with `HERDR_WEB_AUTO_UPDATE=1`, which also permits automatic installation. Some inherited prose in `docs/guide.md` and `docs/app-updates.md` still implies unconditional periodic discovery; the configuration table and executable implementation are authoritative for this baseline. App update builds do not replace the original Herdr-managed plugin checkout, so launcher/manifest changes can still require an explicit plugin reinstall. [Actual timer guard](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/server/updater.ts#L192), [supervisor opt-in](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/server/supervisor.ts#L104), [configuration and stale paragraph](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/docs/guide.md#L444), [launcher limitation](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/docs/app-updates.md#L24)

The **Remote bridge bundles** workflow publishes a separate `remote-vN` release with archives and a SHA-256 manifest to this same fork, only when such a tag triggers it. These are SSH remote runtime assets, not a plugin registry publication. The app has no hardcoded upstream bundle feed: it requires a local manifest or an owner-selected `HERDR_WEB_BUNDLE_MANIFEST`. [Bundle publishing](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/.github/workflows/remote-bundles.yml#L104), [bundle source selection](https://github.com/usergood/herdr-web-ui/blob/c7cdd569b431757a58f771a0369bce1b46c5f291/server/remote-bundle.ts#L10)

## Herdr's own background requests

Removing this app's telemetry and leaving `HERDR_WEB_AUTO_UPDATE=0` does **not** disable Herdr's own update/agent-definition requests. Herdr v0.9.3's release binary starts headless servers with its production policy; that policy enables background checks. Its configuration defaults `[update].version_check` and `manifest_check` to true. Checks run at startup and on a 30-minute schedule. Debug/test builds suppress these checks, but CI downloads a release binary. [Headless production policy](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/server/headless/bootstrap.rs#L54), [policy and timer](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/app/mod.rs#L538), [configuration defaults](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/config/model.rs#L33)

- **Version check:** reads `https://herdr.dev/latest.json` on the stable channel or `https://herdr.dev/preview.json` on preview. Availability/notes are reported; this background operation does not install a new binary. A Homebrew-managed installation checks `https://formulae.brew.sh/api/formula/herdr.json` instead. [Endpoint constants](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/update.rs#L25), [startup check behavior](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/update.rs#L2346)
- **Agent detection definitions:** reads `https://herdr.dev/agent-detection/index.toml`, then retrieves per-agent definition URLs derived from that catalog. It caches valid updates and activates changed definitions automatically. `HERDR_AGENT_DETECTION_MANIFEST_CATALOG_URL` can replace the catalog URL. These are definition downloads, not calls to an AI inference API. [Catalog/update implementation](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/detect/manifest_update.rs#L168), [per-agent requests](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/detect/manifest_update.rs#L239), [fetch implementation](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/detect/manifest_update.rs#L501)

For deterministic CI and fewer external runtime requests, an owned CI configuration can set:

```toml
[update]
version_check = false
manifest_check = false
```

This is a proposed change; no config was changed during this audit. It suppresses those two background check families, not prerequisite/dependency downloads or explicitly requested installations. [Configuration gate](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/app/mod.rs#L541)

## Installer inspection boundary

The exact v0.9.3 source's Unix installer fetches `herdr.dev/latest.json`, then the binary URL selected from that manifest. The Windows CMD wrapper fetches `herdr.dev/install.ps1`; the PowerShell installer fetches the stable or preview manifest and selected assets. A search of the release's `src/` tree and these three installer scripts found no `telemetry`, `sentry`, `posthog`, or `analytics` integration, and the inspected install paths showed no post-install reporting callback. This is a bounded static finding: it does not audit Bun, third-party packages, current remotely served installer revisions, or requests from separately configured plugins and agent processes. [Unix installer](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/distribution/install.sh#L41), [Windows wrapper](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/distribution/install.cmd#L4), [Windows manifest selection](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/distribution/install.ps1#L783)

## Findings to resolve before activation

1. **Stage activation by purpose.** Start with CI only after hardening it; leave Website, Release, live Windows installation and remote publishing disabled until their individual behavior is accepted. Remote bundle validation is useful later, but its tag publishing should have an explicit owner-controlled gate. Individual workflow controls make this possible. [GitHub workflow controls](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)
2. **Pin Actions and downloaded executable installers.** Current `uses:` references are movable major tags such as `actions/checkout@v7` and `oven-sh/setup-bun@v2`; full-SHA enforcement is off. Prefer reviewed immutable commits, least token permissions, and pinned/checksummed prerequisites where feasible. Bundled runtime assets already have explicit checksum pins, but the live Windows Herdr/Bun installers remain remote executable scripts. [GitHub immutable pinning guidance](https://docs.github.com/en/actions/reference/security/secure-use), [token scope](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token), [workflow references](../../.github/workflows/)
3. **Make Herdr CI checks deterministic.** Write the two disabled background-check options above only into each test run's private Herdr configuration, including direct browser and remote smoke paths. Ensure the required detector definitions are pinned before suppressing their refresh; do not change the owner's live Herdr config. [Herdr configuration gate](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/app/mod.rs#L541)
4. **Repair the real Windows update scenario.** The workflow currently passes `-Ref $env:GITHUB_SHA -Update`. The script only chooses the previous release when `-Ref` is empty, so this installs the current commit instead of the previous release. It then waits for `latest_version` without calling the explicit update-check endpoint, although automatic polling is off by default. Inherited tags also select upstream v0.4.3, whose plugin ID differs. Define an owned previous/current fork release pair, request discovery explicitly and verify the update between those releases; keep fresh pinned-commit installation independent of release-history requirements. This is a source finding, not a new Windows execution result. [Workflow arguments](../../.github/workflows/windows-install.yml), [selection and polling](../../scripts/windows-install-e2e.ps1), [actual polling opt-in](../../server/updater.ts)
5. **Force full validation for publication.** The reusable CI change detector falls back to `HEAD~1` outside a PR. A last commit limited to `docs/` can therefore mark code unchanged and skip heavy integration/browser jobs even in a manually dispatched Release/Website validation. Publication should request the full suite independently of PR/documentation filtering. [CI change detector](../../.github/workflows/ci.yml)
6. **Decide the fork's release/catalog policy.** Publish only deliberate fork tags with the Saurons eye identity, correct the Release display title, preserve original attribution and document inherited tags. Direct installation works without marketplace inclusion. Marketplace listing would require an eligible non-fork repository or an upstream policy change; enabling Actions does not resolve that. [Release title](../../.github/workflows/release.yml), [marketplace policy](https://herdr.dev/docs/marketplace/)
7. **Bound artifact retention and review public outputs.** CI uploads reports, fixture screenshots and logs; bundle workflows upload runtime archives/manifests. Workflow files do not specify `retention-days`, so repository settings govern retention. Keep production account keys and provider credentials out of these test jobs. Standard hosted compute is free for this public repository, but artifact/cache storage has separate allowances; review storage settings and budget rather than assuming every aspect is free. [Upload paths](../../.github/workflows/ci.yml), [bundle artifacts](../../.github/workflows/remote-bundles.yml), [current GitHub billing rules](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

No activation, publication or deployment was performed. Only this research note was added; workflow fixes and GitHub setting changes are proposals for a subsequent implementation step.
