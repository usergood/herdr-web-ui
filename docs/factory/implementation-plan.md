# Draft factory implementation plan

The product scope is the complete [specification](specification.md). These are proposed Tickets for owner review, not published issues or executable `ready-for-agent` work. Confirm granularity, dependencies, testing seams and canonical tracker before invoking ticket publication. Each software Ticket should deliver a narrow working path through persistence, server contract, UI and behavioral verification rather than one isolated layer.

## Delivery slices

| Slice | Ticket proposals | Observable completion |
| --- | --- | --- |
| 0 Baseline and skills | P01–P03 | Actual installation reconciled, isolated development configuration reviewed, pinned bundle verified, tracker/provider setup decisions recorded |
| 1 Records and Inbox | P04–P06 | Projectless capture survives restart, defaults and checkout identity work, Project attachment preserves history/artifacts |
| 2 Specification workflow | P07–P09 | Explicit grilling and specification/ticket actions retain questions, versions and approval gates |

| 6 Remote and concurrency | P19–P21 | Laptop execution/reconnect and two independent Implementations work within global capacity; optional third is capped |
| 7 Retro and deployment | P22–P24 | Retro proposals are reviewable, boards/history reflect evidence, backups/rollback and separately scoped promotion are verified |

## Graph and integration rules

The table is the dependency source for this proposal. After owner approval, publish one Ticket per configured tracker record in dependency order, carrying real blocking links and a reference to the accepted spec. If local markdown is chosen, the pinned skill publishes one file per Ticket; this combined proposal is not that publication. [Pinned ticket planning](https://github.com/mattpocock/skills/blob/24fe0ef7737efae15c87225755e9f6f5965e4888/skills/engineering/to-tickets/SKILL.md)

Start only an explicitly selected accepted specification and approved graph. Inside that Run, the coordinator follows the ready Ticket frontier, provisioned worker worktrees and merger role required by [implement-spec](https://github.com/mattpocock/skills/blob/24fe0ef7737efae15c87225755e9f6f5965e4888/skills/engineering/implement-spec/SKILL.md). A newly ready Ticket does not bypass a skill's owner gate. Preserve committed results on the integration branch and serialize its writers; default-branch merge is a separate operation.

## Evidence required per Ticket

Record the specification version, relevant acceptance clauses, public seam used, effective provider/Machine versions, base/head or workspace snapshot, skill/instruction manifest, commands/check results, review results and failures/limitations. UI Tickets include a desktop/mobile acceptance pass with screenshots or recordings from owned test/demo resources. Reuse approved seam decisions within their scope; do not re-confirm merely because a new worker starts.
